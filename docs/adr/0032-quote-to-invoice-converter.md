# 0032 — A domain converter turns an accepted quote into a draft invoice

**Status:** Accepted — 08/10/2026. Refines [ADR 0024](0024-shared-billing-line-and-totals.md) (which left the whole conversion to the use case) and uses the `QuoteId` of [ADR 0026](0026-invoice-create-draft.md).

## Context

P2 starts with the first use case: invoicing a quote. ADR 0024 said the use case "reads the quote and hands its lines to the invoice", with `Quote` and `Invoice` unaware of each other. But the conversion carries business rules: which quotes may be invoiced and what the invoice takes over. Those belong in the domain, not in the orchestration.

Facts in the code that shape the decision:

- A quote's lines can only change in `Draft`; an `Accepted` quote can no longer be modified.
- `BillingLine` is mutable and carries its own `Id` (generated by its constructor). The same instance in a quote and in an invoice would put one line in two aggregates.
- An invoice gets its number, dates and snapshots at issue (`MarkedAsIssued`), not at creation. A `Draft` invoice cannot be cancelled (`Cancelled` only from `Issued`).

## Decision

- **A stateless class in the Domain project** (`QuoteToInvoiceConverter`, chosen by Marine) holds the conversion rules. It knows both types; `Quote` and `Invoice` still know nothing of each other. It reads nothing and writes nothing: `Convert(Quote)` returns a new draft invoice.
- **Rule in the converter:** only an `Accepted` quote can be converted, otherwise `InvalidOperationException`.
- **The draft takes over** the seller id, client id, currency, discount and the quote's `Id` as `QuoteId`. **Lines are copied** with the `BillingLine` constructor (new `Id`), never shared: a line belongs to one aggregate only.
- **No number, no dates, no snapshots at conversion**: they come at issue, as for any invoice.
- **"A quote is invoiced at most once" is checked by the use case**, before calling the converter, through the invoice port (decided by Marine: the converter does not receive invoices). A quote may be invoiced again only if every invoice already linked to it is `Cancelled`.

## Consequences

- The conversion is tested without a database or a repository.
- **Price paid:**
  - the double-billing rule lives in the Application layer, not in the domain: it is tested with the use case and a fake repository, not in the domain tests;
  - the invoice port needs a lookup by `QuoteId` (the exact shape is chosen when the use case is written: statuses only, or a yes/no answer, so that no invoice is loaded just to read a status);
  - checking then inserting does not stop two simultaneous requests: in P3 a unique index in the database (one non-cancelled invoice per `QuoteId`) must back the check;
  - a `Draft` invoice cannot be cancelled, so it blocks a new conversion until it is issued or removed by the repository: a "discard draft" use case will be needed;
  - one more class in the domain, which knows two aggregates.
- Alternatives set aside:
  - **the converter receives the quote's invoices** (or their statuses) and applies the rule itself: the rule would be in the domain and testable without a database, but it moves objects around to read a status; set aside by Marine;
  - **the whole conversion in the use case**: no extra class, but business rules leave the domain;
  - **`Invoice.CreateFrom(Quote)`**: `Invoice` would reference `Quote`, against ADR 0024;
  - **`Quote.ConvertToInvoice()`**: `Quote` would reference `Invoice` and could no longer be tested alone;
  - **a `Converted` status on `Quote`**: not needed (ADR 0029) and it would not allow a conversion after a cancellation.
